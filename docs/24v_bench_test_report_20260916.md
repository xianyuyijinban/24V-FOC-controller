## 3. 改动内容

### 3.1 电压阈值修改（你明确要求的第 2 条）

**文件**: `MDK-ARM/code/foc_app.h:118-119`

```diff
-#define FOC_DEFAULT_OVERVOLTAGE_LIMIT_V   18.0f   /* 12V系统过压阈值 V */
-#define FOC_DEFAULT_UNDERVOLTAGE_LIMIT_V  10.0f   /* 12V系统欠压阈值 V */
+#define FOC_DEFAULT_OVERVOLTAGE_LIMIT_V   28.0f   /* 24V系统过压阈值 V (24V 母线 +4V 裕量) */
+#define FOC_DEFAULT_UNDERVOLTAGE_LIMIT_V  14.0f   /* 24V系统欠压阈值 V (24V 母线 -10V 裕量) */
```

**为什么必须改**：母线实测 23.97V > 原过压阈值 18V，
`appWarningFlags` 常置 `0x00000002`（`VBUS_OVERVOLTAGE_BIT`）。

**取值依据**：
- 过压 28V = 24V 母线 +4V 裕量（原 12V 方案为 12V+6V=18V，比例更保守）
- 欠压 14V = 24V 母线 −10V 裕量（原 12V 方案为 12V−2V=10V；14V 留出足够跌落容限，
  且高于严重跳闸线 `14−1.0=13.0V`）
- ⚠️ **这两个值是 12V 方案按比例外推的，不是电机耐压实测值。**
  我不知道这块板功率级的实际耐压上限（DRV8350S 本身支持高压，但整板/电机未知）。
  **请你确认 28V 是否合适**，不合适我改。

### 3.2 关于运行时命令 `CMD:VBUS_LIMIT`

发现运行时命令本来就能改阈值（我一开始误判它不存在，因为它**静默无应答**）：

```
CMD:VBUS_LIMIT,14,30  →  N 帧 uv/ov 字段立刻变为 14.00/30.00 ✓
```

但它**不落 Flash**（`ParamPackage_t` 只含电机参数，无电压字段），
断电即回默认值。所以**编译期默认值也必须改**——否则下次重启就退回 18V。

**当前状态**: 编译期 14/28 已烧入；运行时又额外发过一次，两者当前一致。

## 5. 结果分析（原始值全摆）

### 5.1 B 序列（6° 阶跃 + 斜坡 @2°/s）

**阶跃到位率 @2.8s（核心验收判据，≥96.7% 为过）**

```
100.3  98.9  100.0  99.7  99.7  99.7  98.9  99.1  99.8  99.1
 99.2  99.8   98.6  99.5  98.5 103.4 108.8

n = 17   min = 98.5%   max = 108.8%   →  17/17 轮全部 PASS ✓
```

> 由 2 个 run（COG OFF 2 轮 + COG ON 15 轮）合并统计。
> 末两轮 103.4 / 108.8 是**阶跃本身的小超调**（>100%），
> 量级远小于 5.1 节斜坡超调，属正常阶跃响应，不影响判据。

**斜坡超调 track%（历史 S2 带 124.2–146.9%，中位约 133%）**

```
138.0 (cog=0)   137.0 (cog=0)
147.9 (cog=1)   149.3 (cog=1)   172.7 (cog=1)
156.6 (cog=1)   160.5 (cog=1)   134.8 (cog=1)   142.9 (cog=1)   111.4 (cog=1)

n=10  min=111.4  max=172.7  mean=145.1  median=147.9  spread=61.3
高于历史带上沿 146.9% 的轮次: 5/10
```

**⚠️ 这是本次唯一实质性问题。**

判读（严格按你的"禁止合理化故事"纪律，不找补）：

1. **不能归因于电压阈值改动** —— 阈值只影响告警位，与位置环控制律无关。
2. **分散度极大（111–173%）**，说明这是**随机性/多稳态**现象，不是稳定偏置。
   你的 PROGRESS `[2026-09-10]` 对同一现象的原话正是：
   *"臂差淹没在重复性内"*、*"定版复跑自身跨度 18.9 点"*。本次跨度 61.3 点，
   比那 18.9 点更大。
3. **历史带 124.2–146.9% 本身也是 S2 电压模式的散点**，且你当时已把该案**关闭**，
   结论是"两模式同量级"、"comp 非过冲主控"。
4. 因此我的判断是：**超调在 24V 下偏大，但当前 10 轮样本不足以判定它是真实劣化
   还是同一多稳态现象的更宽尾部。** 我没有足够数据下结论，**不下结论**。
5. COG ON（cog=1）的轮次里既有最低的 111.4%，也有最高的 172.7%，
   **看不出 COG 与超调的方向性关联**。

**建议**：若你要钉死这一点，需要按你 9/10 那套"任务卡"重新设计判别实验
（锁协议版本、控温、固定起始角度、加大 N），当前数据不支持任何因果结论。

## 6. 未决 / 存疑项（如实记录，不做合理化）

### 6.1 编码器 `data_valid=0` 矛盾（未解）

```
TLE_RAW,raw=0xA0D0,safety=0x7E97,status=0x00,
        recv_crc=0x97,calc_crc=0x97,data_ok=1,crc_error=1,valid=0,angle=92.29
```

- `recv_crc == calc_crc`（0x97），`data_ok=1`（safety word bit13/bit12 均置位），
  `safety_ok && raw_angle!=0` → 按代码逻辑应走 `data_valid=1` 分支
- **但 `valid=0`** —— 我逐行核对了 `tle5012.c:349-368`，两条路径都置 1，
  找不到置 0 的路径
- N 帧 `encDet=0` 与此一致
- **但角度读数完好**：92.29° 长期稳定、带动正确（100.42°）、控制性能正常

**结论：状态标志与可观测行为矛盾，我无法解释。** 未做进一步侵入式诊断
（需要在线调试或插桩），**留给你裁定**。不影响本次测试结果的有效性
（位置闭环用的是角度值，实测表现正常）。

### 6.1b 探针结果 + 本项关闭（2026-09-16，FW1.5.1）

FW1.5.1 给 `CMD:TLE_RAW` 追加了 `spi_err` / `crc_total` 两字段后探针如下：

```
T0   : TLE_RAW,...,data_ok=1,crc_error=0,valid=1,angle=110.19,spi_err=0,crc_total=1621
T+10 : TLE_RAW,...,data_ok=1,crc_error=0,valid=1,angle=110.19,spi_err=0,crc_total=1621
T+20 : TLE_RAW,...,data_ok=1,crc_error=0,valid=1,angle=110.20,spi_err=0,crc_total=1621
```

**结果 = 第三种（卡内预判）：`valid=1`，历史瞬态遗留，本项关闭。**

- `valid` 与 N 帧 `encDet` 均已恢复为 `1`，`crc_error=0`
- `spi_err=0` **且 20s 内零增长**（期间编码器 ~5kHz 读取约 10 万次）→
  **不存在进行中的通信故障**，卡内"周期末通信故障每轮重盖旗"假说**证伪**
- ⚠️ 诚实说明：`spi_error_count` / `crc_error_total` 是 **RAM 计数器**
  （`TLE5012_Init` 清零），烧录后重启即从 0 起算，所以 `spi_err=0` 本身不是
  强证据；真正有意义的是**静止 20s 零增长**
- **新发现**：`crc_total=1621` 非零且**静止** —— 说明本次开机后曾发生过一簇
  CRC 错误（约 1621 次）后自行恢复。这与"原先 `valid=0` 是瞬态"自洽
- **关闭依据**：原观测（`valid=0`/`encDet=0`，2026-09-15 23:5x）→ 间歇
  （2026-09-16 00:0x 期间 `valid` 时好时坏）→ 现已稳定 `valid=1`。
  按卡内判定"valid=1 了 → 历史瞬态遗留，关案"

**残留待办（不属本卡）**：那 1621 次 CRC 的成因未查（何时发生、由何触发）。
本次未动 `tle5012.c` 任何标志逻辑（遵守卡内禁区）。
